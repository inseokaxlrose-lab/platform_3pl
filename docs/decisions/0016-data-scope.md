# 0016. 데이터 범위 (전체 / 소속 센터 / 자기 화주사)

- 날짜: 2026-11-13
- 상태: 채택
- 관련: PRD 3장 "핵심 원칙", 0003 결정 7, 0015 (서버 액션)
- 코드: `src/lib/scope/`

## 권한과 데이터 범위는 별개

| | 질문 | 정하는 것 |
|---|---|---|
| 권한 | 무엇을 할 수 있나 | 권한그룹·사용자 예외 (0013) |
| 데이터 범위 | 어떤 데이터를 볼 수 있나 | 사용자 유형 + 소속 |

## 결정

### 소속 모델 (최소)

- `center`, `shipper`: 코드·이름·사용 여부만. 자세한 정보·관리 화면은 M2(센터)·M3(화주사).
- 센터 직원 ↔ 센터: **여러 개 가능** (`user_center`). 두 센터를 함께 맡는 관리자 대비.
- 화주사 사용자 → 화주사 1개 (`user.shipperId`).
- **DB CHECK** `user_shipper_matches_type`: 화주사 사용자만 화주사 연결을 가진다. 프로그램을 거치지 않은 변경도 막는다.
- `createUserAccount`: 센터 직원은 센터 1개 이상, 화주사 사용자는 화주사 필수, 다른 유형의 소속은 거부.
- 직원이 소속된 센터, 사용자가 소속된 화주사는 삭제할 수 없다 (Restrict).

### 범위 계산 (`computeScope`)

| 사용자 | 범위 |
|---|---|
| 운영사 | `ALL` |
| 센터 직원 | `CENTERS` (소속 센터 중 사용 중인 것) |
| 화주사 사용자 | `SHIPPER` (화주사가 사용 중일 때) |
| 소속 없음·소속이 모두 사용 중지·계정 사용 중지·로그인 안 됨 | `NONE` (아무것도 못 봄) |

- **애매하면 막는다**: 소속 없는 센터 직원은 "전체"가 아니라 `NONE`.

### 적용

```ts
// 목록 조회
prisma.asn.findMany({ where: { ...scopeFilter(scope, { center: 'centerId', shipper: 'shipperId' }), ...검색 } })
// 관계를 거치는 칸: { center: 'warehouse.centerId' }
// 한 건 수정·삭제
assertInScope(scope, asn, { center: 'centerId', shipper: 'shipperId' })  // 범위 밖이면 '대상을 찾을 수 없습니다.'
```

- 서버 액션: `createAction` 처리 함수가 `scope`를 받는다. 화면(서버 컴포넌트): `getCurrentScope()`.
- **필요한 칸을 지정하지 않으면 오류**(`ScopeFieldMissingError`): 조건 없이 조회돼 전체가 보이는 사고를 막는다. 예) 화주사 칸이 없는 표를 화주사 사용자 범위로 조회.
- 범위 밖 한 건은 "찾을 수 없음": 다른 화주사 데이터의 존재 여부도 알려주지 않는다.
- Prisma 확장으로 모든 쿼리에 자동으로 붙이는 방식은 쓰지 않는다: 어디에 범위가 걸리는지 코드에서 보이지 않고, 칸 이름이 표마다 달라 실수하기 쉽다. 명시적 도우미 + 테스트로 지킨다.

## 나중에

- 센터 직원이 볼 수 있는 화주사 = "그 센터를 이용하는 화주사" → M3의 화주사 ↔ 이용 센터 연결 후 적용.
- ASN·재고 실제 쿼리 적용과 "다른 화주사 데이터 접근 불가" 통합 테스트 → M4·M5.
