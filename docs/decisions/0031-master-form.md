# 0031. 기준정보 입력 화면 공통 틀 + 운영사 화면 적용

- 날짜: 2026-11-15
- 상태: 채택 (0002 결정 3 "좌우 2단 배치"를 기준정보 화면에서 대체)
- 관련: 0002 (UI), 0024 (운영사 정보), 0029 (번호 숫자 저장), 0030 (공통코드), 0015 (서버 액션)
- 가이드: `docs/ui-guidelines.md` · 견본: `/dev/components`
- 코드: `src/components/master-form/`, `src/components/inputs/`, `src/app/admin/master/company/`

## 배경

운영사 화면의 문제: 좌우 50% 2단이라 무게가 맞지 않고 빈 공간이 큼, 짧은 값도 긴 입력칸, 카드 안의 카드(테두리 중첩), 담당자를 카드로 늘어놓아 세로로 김, 담당 업무가 자유 글자, 저장 버튼이 우하단에 홀로, 취소·변경 감지 없음. 앞으로 섹션(물류 자격·운영 기본값·계약·요금제)이 늘어날 예정이라, 화면이 적은 지금 공통 틀을 만든다.

## 결정

### 화면 틀

- **제한 폭 한 단 + 12칸 격자**: 본문 `max-w-5xl` 가운데, 칸 너비는 `Field span`(1~12). 좁은 화면은 한 줄 전체.
- **섹션**: `sections` 배열 (id·제목·설명·내용). 카드 대신 구분선. 넓은 화면(lg)은 왼쪽에 **섹션 목차**(지금 보는 섹션, 오류 섹션 빨간 점). 새 섹션은 배열에 추가만 하면 된다.
- **아래 고정 저장 막대**: 변경사항 있음 · [취소] · [저장]. 변경이 없으면 꺼진다.
- **동작은 `useMasterForm`**: 값·오류·변경 감지(JSON 비교)·취소(마지막 저장 값으로)·저장(화면 검사 → 서버 액션 → 성공 값이 새 기준 → `router.refresh`).
- **첫 오류 칸으로 이동**: 저장 시도마다 `aria-invalid="true"`인 첫 칸으로 스크롤·초점.
- **이탈 경고** (`useDirtyGuard`): 새로고침·창 닫기는 `beforeunload`, 화면 안 링크는 문서 클릭을 먼저 받아 막고 확인 창. 브라우저 [뒤로]는 막지 못한다(App Router에 이동 직전 알림이 없음) — 알려진 제약.
- 서버 액션의 입력 오류 위치를 **전체 경로**(`contacts.0.phone`)로 바꿨다 (`createAction`의 `toFieldErrors`). 전에는 맨 위 칸 이름(`contacts`)까지만이라 행별 서버 오류를 칸에 붙일 수 없었다. 맨 위 칸 오류는 이전과 같은 모양.

### 입력 부품 (`@/components/inputs`)

- `BizNoInput`·`CorpRegNoInput`·`PhoneInput`: 값은 숫자만, 화면은 자동 하이픈. 커서는 "커서 앞 숫자 개수" 기준으로 제자리 유지.
- `EmailInput`, `AddressInput`([우편번호][주소 검색] 한 줄 → 기본주소 → 상세주소, 값 모양은 기존 API의 `zipCode/address/addressDetail` 유지), `CodeSelect`(그룹만), `NumberInput`(쉼표·소수 자리·최소/최대·단위), `DateInput`/`DateRangeInput`(브라우저 기본 날짜 칸, 새 라이브러리 없음), `YnToggle`(값 boolean — DB가 Boolean이라 'Y'/'N' 글자를 쓰지 않음, shadcn switch 추가, `radix-ui`는 이미 설치돼 있어 새 패키지 없음).
- 아직 쓰는 화면이 없는 부품(법인번호·숫자·날짜·Y/N)도 화주·품목 화면에서 곧 쓸 것이 확실해 만들고 견본에 올렸다 (사용자 동의).

### 1:N 표 (`EditableSubTable`)

- 열 정의(키·이름·필수·너비·입력 종류 또는 render), 최대·최소 행, 하나만 고르는 칸(primary), 행 오류·표 오류.
- 삭제는 확인 없이 바로(저장 전 [취소]로 복구). 처음 추가한 행이 자동 대표, 대표를 지우면 남은 첫 행이 대표.
- 넓은 화면은 한 행 한 줄, 좁은 화면은 세로 블록.

### 공통 검증 규칙

- `requireOneOf(keys, 문구)`: 둘(이상) 중 하나 필수, 오류는 첫 칸에.
- `exactlyOne(key, 문구)`: 목록에 행이 있으면 정확히 1개 (행이 없으면 통과).

### 운영사 화면

- 섹션: 기본 정보(회사명 8, 사업자번호 4, 대표자 4, 업태 4, 종목 4) / 연락처·주소(대표 전화 4, 팩스 4, 대표 이메일 8, 주소 12) / 담당자.
- 담당자: 담당 업무(공통코드 `CONTACT_DUTY`)* · 담당자명* · 연락처 · 이메일 · 대표(1명 필수) · 삭제. 연락처·이메일 중 하나 필수.
- 서버는 담당 업무가 사용 중인 공통코드인지 확인한다. 이미 저장돼 있던 코드는 그 사이 사용 중지됐어도 그대로 둘 수 있다. `code-usage.ts`에 등록해 쓰이는 코드는 지울 수 없다.
- API 요청·응답 모양은 담당자에 `isPrimary`가 늘고 `duty`가 코드가 된 것 외에는 그대로.

## 기존 데이터 (마이그레이션 `contact_duty_code`)

- `company_contact.isPrimary` 추가, 회사마다 첫 번째 담당자를 대표로.
- 담당 업무 글자 → 코드: "입고"가 들어가면 INBOUND, "출고·배송" OUTBOUND, "재고" INVENTORY, "정산·청구" SETTLEMENT, "계약·영업" CONTRACT, "IT·전산·시스템" IT, 나머지 ETC. 원래 글자는 남기지 않는다(개발 데이터 2건: 입고 문의 → INBOUND, 정산 → SETTLEMENT).

## 옮기기 (2026-11-15 완료)

- 운영사·센터·창고·사용자·권한그룹 등록·수정을 모두 이 틀로 옮겼다. `FormColumns`는 지웠다.
- 틀 보강: **따로 처리하는 섹션**(`standalone`: 자기 버튼으로 바로 처리하는 상태 변경·요약 표·개별 권한·계정 관리 — 폼 밖에 그려 저장 막대·변경 감지에서 빠짐, 폼 안의 폼 방지), **저장 후 동작**(`onSuccess`: 등록 → 수정 화면 이동 → 2026-11-17 `createdHref`로 바꿈: 등록 화면에 머물며 [등록한 항목 보기]·[계속 등록], 여러 건을 이어서 등록). 저장 버튼은 `form` 속성으로 폼과 연결.
- 수정 화면은 저장 후 그 자리에 남는다(전에는 목록으로 이동). 목록 복귀는 제목 오른쪽 [목록](검색 조건 그대로).
- 사용자·권한그룹 입력 규칙을 화면·서버 공용으로 옮겼다(`src/lib/users/user-schema.ts`, `src/lib/permissions/role-schema.ts`). 사용자 소속 규칙은 이제 칸 오류(`centerIds`/`shipperId`)로 돌아온다.
- 고친 문제: 목차가 그릴 때마다 다시 관찰해 화면이 멈출 수 있던 것(섹션 id 목록으로 비교).
