# 0046. 마이너스 재고 방지 · 동시 처리 안전성 · 재고 트랜잭션 다시 시도

- 날짜: 2026-11-15
- 상태: 채택 (M4 마지막 작업 — M4 완료)
- 관련: 0045 (재고 변경 공통 함수), 0044 (재고 모델)

## 확인한 것 (`stock-concurrency.db.test.ts`, 서로 다른 DB 연결·트랜잭션으로 정말 동시에)

| 상황 | 결과 |
| --- | --- |
| 아직 없는 주소에 입고 20건 동시 | 재고 줄 1줄, 수량 = 합계 (`INSERT … ON CONFLICT DO NOTHING`) |
| 재고 10에서 −1 조정 20건 동시 | 정확히 10건 성공·10건 "재고 부족", 수량 0, 변동 후 수량 9…0이 한 번씩 (마이너스·겹침 없음) |
| 수량 10·할당 4에서 이동 10건 동시 | 6건만 성공, 할당분 4 남음 |
| A→B·B→A 이동 20건 동시 (다시 시도 없이) | 교착 없이 모두 성공, 수량 제자리 — 함수 하나는 키 순서로 잠근다 |
| 입고·이동·조정 섞어 동시 | 재고 줄마다 이력 합계 = 수량, 음수 없음 |

- **변이 확인**: 잠금 순서 정렬을 빼면 A↔B 이동 테스트가 교착으로 실패한다 → 테스트가 실제로 순서 규칙을 지킨다.
- 같은 테스트를 3번 연속 실행해 흔들리지 않음을 확인.

## 결정 (사용자 결정, 2026-11-15): 여러 줄 교착 → 자동 다시 시도(추천안)

한 트랜잭션에서 여러 재고 줄을 바꾸면(예: 입고 확정의 여러 라인) 두 요청이 반대 순서로 잠가 교착이 생길 수 있다. PostgreSQL이 한쪽을 실패시킨다.

- `src/lib/stock/stock-transaction.ts`의 **`stockTransaction(fn)`**: 재고를 바꾸는 업무 저장은 `prisma.$transaction` 대신 이것을 쓴다. 교착(40P01)·직렬화 실패(40001)면 트랜잭션 전체를 짧게(시도마다 길게 + 무작위) 쉬었다가 최대 3번까지 다시 실행. 실패한 시도는 DB가 전부 취소했으므로 두 번 저장되지 않는다(테스트: 교차 이력 정확히 4줄).
- 업무 오류(재고 부족 등)는 다시 시도하지 않는다.
- 잠금 대기가 있어 연결 대기 10초·실행 20초로 기본값보다 넉넉히.
- **오류 알아보기(`isRetryableTxError`)**: Prisma가 알려 주는 모양이 쿼리마다 다르다 — 줄 잠금(직접 SQL)에서 난 교착은 `P2010` + `meta.driverAdapterError.cause { originalCode: '40P01', kind: 'TransactionWriteConflict' }`였다(테스트로 확인). 그래서 코드 하나에 기대지 않고 오류 안쪽까지 따라가며 찾는다.
- 그래도 여러 줄을 처리할 때는 품목·로케이션 순으로 정렬해 부르면 교착 자체가 줄어든다(권장).
