## 결정

### 거래처와 납품처를 나눈다

- 거래처(`tb_customer`)는 주문 상대(본사), 납품처(`tb_ship_to`)는 실제로 물건을 받는 곳이다. 거래처 1 : 납품처 N.
- 거래처의 옛 배송지 칸(받는 사람·배송 메모·배송센터)은 지웠다. 마이그레이션이 기존 배송지를 **기본 납품처**로 옮긴다.
- 납품처 규칙
  - 코드는 거래처 안에서 고유(부분 고유 인덱스, 지운 줄 제외), 등록 후 수정 불가.
  - **기본 납품처는 정확히 1곳**(부분 고유 인덱스), 사용 중 납품처 1곳 이상.
  - 납품처 없이 거래처를 등록하면 거래처 주소로 기본 납품처를 만든다(`system_created_yn = 'Y'`, 코드·이름은 거래처와 같게).
  - 기본 납품처의 **거래처 주소 동기화**(`addr_sync_yn`): 켜 두면 거래처 주소를 바꿀 때 납품처 주소·배송센터도 다시 정한다.
- 원본 주소(`raw_*`)와 정제 결과(`zip_cd`·`addr`·`bjd_cd`·`addr_grade` 등)를 따로 저장한다. 화면 입력 칸에는 원본을 보여 준다.

### 배송센터 지정 (`assignShipToCenter`)

1. 주소 정제(`normalizeAddress`) → 권역 기준 센터(`resolveCenterByAddress`) → 화주 이용 센터(ShipperCenter ACTIVE) 확인.
2. 센터를 직접 고른 경우: 없는 센터 `INVALID_CENTER_CD`, 이용 센터 아님 `NOT_CLIENT_CENTER`, 일시중지·폐쇄 `CENTER_INACTIVE`. 통과하면 지정 구분 `MANUAL`(화면)·`IF`(연동). 권역 기준과 다르면 `region_mismatch_yn = 'Y'`.
3. 고르지 않은 경우(권역 자동): 권역 결과가 없으면 `REGION_UNASSIGNED`·`REGION_MIXED`, 정제 실패·등급 미달이면 `ADDR_NOT_RESOLVED`. 통과하면 `AUTO`.
4. 정하지 못하면 **"확인 필요"(`NEED_CONFIRM`) + 사유 코드**로 저장한다. 반려는 연동 정책이 `AUTO_REJECT`·`REQUIRED`일 때만(③ API에서 사용). 화면 저장은 늘 저장하고 메시지로 알린다.
5. 주소와 센터 선택을 바꾸지 않은 납품처는 다시 계산하지 않는다. 연동으로 받은 지정(`IF`)을 화면 저장이 덮어쓰지 않게 하기 위함이다.
6. 권역설정이 바뀌면 `AUTO`만 따라 바뀐다(② 단계에서 연동).

### 값 목록

- 프로그램이 값에 따라 동작을 바꾸는 값(거래처 상태, 주문 주소 방식, 등록 경로, 납품처 상태, 지정 구분·상태·사유)은 **상수 + DB 검사 조건**(`customer-codes.ts`, 0040)으로 둔다.
- 거래처 유형만 공통코드 `PARTNER_TYPE`.
- 거래처 상태는 거래중 / 거래중지. 거래중지는 신규 출고요청만 막는다(출고 작업에서 적용).

### 화면

- 거래처 편집에 "납품처" 섹션을 둔다(표 + 오른쪽 드로어). 드로어 [적용]은 화면 값만 바꾸고, 거래처 [저장] 한 번에 함께 저장한다.
- 드로어는 주소를 고르면 "이 지역의 기본 배송센터"를 미리 보여 준다(`previewShipToCenterAction`). 직접 고른 센터가 다르면 권역 불일치를 경고한다.
- 저장 뒤 편집 페이지는 `key={rowVersion}`으로 다시 그려 새 납품처 키와 지정 결과를 보여 준다.
- 목록: 기본 납품처 지역(시군구)·배송센터·납품처 수·확인 필요 건수, "배송센터 확인 필요" 거르기, 거래중지/거래재개 일괄.

### 다시 정하기 (`reassignShipTos`) — 한 함수, 모드 4가지

- `REGION`(권역설정 저장 직후)·`RENORMALIZE`(재정제, 정제 캐시 안 씀): 지정 구분을 지킨다.
  - 권역 자동·확인 필요 → 주소로 다시 계산(정해지면 지정 완료).
  - 수동·연동 → 센터·구분·지정 시각은 그대로, 권역 기준 센터와 불일치만 새로. 센터가 이용 불가가 되어도 센터는 두고 사람이 판단한다.
- `AUTO`(권역 기준으로 재지정): 수동·연동을 버리고 권역 자동으로.
- `MANUAL`(배송센터 일괄 지정): 고른 센터로 지정. 그 화주의 이용 센터가 아니거나 사용 중이 아니면 **건너뛰고**(기존 값 유지) 결과에 알린다.
- 바뀐 납품처의 **거래처 버전을 올린다** → 열어 둔 거래처 화면이 옛 지정으로 덮어쓰지 못하고 충돌로 막힌다.

### 권역설정 변경 연동

- 영향 대상(`shipTosInZips`): 정제 우편번호가 바뀌는 우편번호인 납품처 + 법정동·시군구로 추정한 납품처 중 법정동이 그 우편번호에 속한 곳.
- 미리보기(`shipToRegionImpact`): "자동 지정 납품처 n곳 센터 변경 · 수동·연동 지정 납품처 n곳 권역 불일치 발생 · 확인 필요 납품처 n곳 다시 지정 · 법정동·시군구 추정 n곳 다시 계산". 엑셀 업로드 검증 요약에도 붙는다.
- 저장(트리·표·붙여넣기·엑셀 업로드): 센터가 바뀐 우편번호만(추천 확인은 제외) `REGION` 모드로 다시 정한다.
- 온도대별 배정 행은 납품처에 쓰지 않는다(전체 배정만 — 온도대별 납품처 센터는 2차).
- 남은 일(정의서 5번 중): 지역 마스터 갱신 뒤 C·D·F 재정제 배치, 화주 이용 센터 추가·종료 때 NOT_CLIENT_CENTER 재시도 — 지금은 납품처 목록의 [재정제]·[권역 기준으로 재지정]으로 처리한다.

### 납품처 목록 (`/admin/master/ship-tos`)

- 빠른 보기 [확인 필요] [권역 불일치] [정제 등급 C 이하] + 화주·배송센터·지정 상태, 상세 조건(지정 구분·사유·불일치·등급·시군구·등록 경로·상태).
- 일괄 처리 결과(지정 완료·확인 필요·건너뜀)는 도구줄에 글로 보여 준다.

### 하나의 upsert 서비스 (`upsertPartner`, `customer-upsert.ts`)

- API와 엑셀 업로드가 같은 함수를 쓴다. 입력은 연동 이름(`partnerSchema`), 저장은 화면과 같은 `createCustomerIn`·`updateCustomerIn`.
- **보낸 칸만**: 지금 값(`customerInputOf` — 수정 화면과 같은 변환)에 보낸 칸만 덮어쓴 뒤 화면과 같은 입력 규칙으로 검사한다. `null`은 지우기, 안 보낸 칸은 그대로.
- **보낸 납품처만**: 지금 납품처 목록에 보낸 납품처를 덮어쓰거나 뒤에 붙인 전체 목록으로 저장한다(`partial` — 빠진 것을 지우지 않음).
- **UNCHANGED**: 입력 규칙을 거친 값(하이픈 없는 전화 등)으로 비교해 같으면 아무것도 쓰지 않는다. 납품처 저장도 바뀌지 않은 줄은 쓰지 않는다(수정일·버전 그대로).
- **연동 센터코드**: 납품처 입력에 `centerMode: 'IF'` + `centerCode`를 더했다(화면은 AUTO·MANUAL만). 같은 센터코드를 다시 보내면 지정을 그대로 둔다.
- **정책 반려**: `collectRejects`면 반려된 납품처만 저장하지 않고 결과에 FAIL. 새 기본 납품처가 반려되면 옛 기본으로 되돌리고, 기본이 없어지면(새 거래처의 유일한 납품처 반려 등) 거래처도 실패시킨다.
- 오류코드: 입력 규칙의 `params.apiCode`(기본 1곳·사용 중 1곳·주소 필수)와 칸 위치(코드 형식)로 `DEFAULT_SHIP_TO_REQUIRED`·`LAST_SHIP_TO_INACTIVE`·`PARTNER_ADDRESS_REQUIRED`·`PARTNER_CD_INVALID`·`SHIP_TO_CD_INVALID`를 정한다. 센터 반려 사유는 그대로 코드(`ADDR_NOT_RESOLVED`만 `ADDRESS_NOT_RESOLVED`). 정의서의 9개에 `CENTER_INACTIVE`·`REGION_UNASSIGNED`·`REGION_MIXED`를 더했다(자동 반려 사유를 구분).

### API (`src/lib/api/endpoints/partners.ts`)

- 등록은 **건마다 따로 트랜잭션**(`writeTransaction`) — 한 건 실패가 다른 건을 되돌리지 않는다. TEST 키는 건마다 계산 후 되돌린다.
- API 틀 확장: 경로 값(`ctx.params`, Next 라우트의 두 번째 인자)과 건별 덧붙임 결과(`extra` → `items[].shipTos`).
- 목록은 키 순서 + `cursor`(마지막 키), `updatedAfter`는 수정일시 조건. 응답의 전화·사업자번호는 숫자만.
- 연락처·이름은 요청 로그에서 가린다(기존 마스킹 규칙: `receiverNm`·`receiverTelNo`·`addr*`).

### 엑셀 업로드 (`customer-upload.ts`)

- 검증도 **파일 전체를 한 트랜잭션에서 실제로 처리해 본 뒤 되돌린다** → 미리보기에 신규·수정·변경 없음·배송센터 지정/확인 필요 건수.
- 등록 경로 `UPLOAD`, 화주 정책은 쓰지 않는다(운영사가 올림).
- 엑셀은 빈 칸 = 안 보냄이라 값을 지울 수 없다(화면에서 지운다).

## 버린 안

- **납품처를 따로 저장하는 별도 화면만 두기**: 거래처를 만들 때 납품처까지 한 번에 넣는 일이 대부분이라, ① 단계는 거래처 화면 안에서 함께 저장한다. 많은 납품처를 다루는 목록 메뉴는 ②에서 만든다.
- **화면 저장 때도 정하지 못하면 반려**: 권역설정이 아직 덜 된 운영 초기에 거래처 등록이 막힌다. 저장하고 "확인 필요"로 모아 처리하게 했다.
