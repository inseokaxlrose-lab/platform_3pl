# 0013. 최종 권한 계산 규칙

- 날짜: 2026-11-13
- 상태: 채택
- 관련: 0003 결정 7, 0010 (권한 DB 모델), 0011 (권한 코드)
- 코드: `src/lib/permissions/compute-permissions.ts` (순수 함수), `load-user-permissions.ts` (DB 조회)

## 기본 공식

최종 권한 = (속한 모든 그룹의 권한 합) + 사용자 추가(GRANT) − 사용자 제외(DENY)

## 공식만으로 애매한 경우의 규칙

| # | 경우 | 처리 | 이유 |
|---|---|---|---|
| 1 | 그룹에 있는데 사용자 제외 | 제외가 이긴다 | 예외를 주려고 일부러 설정한 것 |
| 2 | 여러 그룹에 같은 권한 | 하나로 합친다 | |
| 3 | 목록(`permissions.ts`)에 없는 옛 코드 | 무시, `ignored`(reason `unknown`)로 알림 | 메뉴 삭제 후 남은 찌꺼기로 이상한 권한이 생기지 않게 |
| 4 | 사용자 유형과 다른 영역의 코드 (화주사 ↔ 운영사 화면) | 무시, `ignored`(reason `other-area`)로 알림 | 데이터 범위 원칙을 계산 단계에서 한 번 더 지킨다. 그룹을 잘못 넣어도 화주사에게 운영사 권한이 생기지 않는다 |
| 5 | 버튼 권한은 있는데 그 메뉴의 조회(`read`)가 없음 | 그 메뉴의 버튼 권한도 무효 | 메뉴에 못 들어가는데 버튼만 누를 수 있으면 안 된다. "조회 제외 = 메뉴 전체 차단"으로 쓸 수 있다 |
| 6 | 사용 중지 계정 | 권한 없음 | |

- 같은 사용자·같은 코드에 추가와 제외가 동시에 있을 수는 없다 (DB 기본키, 0010).
- 5번 때문에 권한그룹 관리 화면에서는 버튼 권한을 체크하면 조회도 자동으로 체크되게 한다 (관리 화면 작업에서).
- `ignored`는 권한그룹·사용자 관리 화면에서 "정리가 필요한 권한"으로 보여줄 수 있다.

## 테스트

- 단위 12개: 기본 공식 + 위 6가지 + 그룹 없음·추가만 있음 등
- DB 4개: 실제 저장 → 조회 → 계산
