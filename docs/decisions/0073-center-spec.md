# 0073. 센터 정보 확장 (컬럼 정의 반영, 운영 상태 4단계, 대기 창고 3개, 상속 설정)

- 날짜: 2026-11-16
- 상태: 채택 (사용자 결정 4가지 — 아래 "결정")
- 관련: 0025 (코드 3층), 0026 (센터), 0031 (입력 화면 틀), 0038 (공통 칸·논리 삭제), 0040 (운영사 정보), 0045 (재고 변경)

## 배경

센터는 이름·전화·주소·센터장 정도만 있었다. 실제 운영에는 센터 유형, 운영 상태, 시설(면적·도크·온도대·보세),
운영 시간·마감 시각, 기본 로케이션, 여러 담당자가 필요하다. 사용자가 컬럼 정의(1차·2차)를 주었다.

- **1차**: DB + API + 화면
- **2차**: DB + API만 (기본값, 화면은 나중에) — 토지면적·층수·층고·팔레트 수용량, 창고업 등록번호·GLN, 보세 세부(종류·특허번호·구역·세관), 위험물·식품·의약품, 타임존·할당 규칙·로트/유통기한/시리얼 관리(상속)

## 결정

| 항목 | 정한 것 |
| --- | --- |
| 센터코드 | **필수·불변**, 영문 대문자·숫자 1~20자 (소문자는 대문자로). 비우면 시스템 코드로 채우던 방식은 없앰 |
| 운영 상태 | `PREPARING` 준비중 / `ACTIVE` 운영중 / `SUSPENDED` 일시중지 / `CLOSED` 폐쇄. 예전 `INACTIVE` → `SUSPENDED`로 옮김 (사유 "기존 사용 중지에서 옮김") |
| 대기 창고 | 입고대기 + **출고대기·반품대기**를 센터마다 자동 생성, 기존 센터도 마이그레이션으로 보정. 각 DEFAULT 로케이션이 센터의 기본 입고·출고·반품 로케이션 |
| 담당자 | 예전 `manager_nm`·`manager_tel_no` 두 칸은 남기고, 담당자 표 `tb_center_contact` 추가 (최대 10명, 대표 1명) |
| 담당자·온도대 표 | 등록·수정자/일시 칸을 둔다 (줄 키로 고치는 저장이라 등록 정보가 남는다) |

### 상태별로 할 수 있는 일

| | 준비중 | 운영중 | 일시중지 | 폐쇄 |
| --- | --- | --- | --- | --- |
| 새 업무 (입고·재고·출고·배송 센터) | ✕ | ○ | ✕ | ✕ |
| 기준정보 준비 (창고·배송권역 추가, 화주사 이용 센터, 사용자 소속) | ○ | ○ | ✕ | ✕ |
| 소속 직원의 데이터 범위 | ○ | ○ | ○ | ✕ |
| 센터 정보 수정 | ○ | ○ | ○ | ✕ (읽기 전용) |

- 코드: `src/lib/centers/center-status.ts` — `CENTER_SETUP_ONLY`·`isCenterSetupStatus`·`isCenterInScopeStatus`. 새 업무 조회는 기존 `ACTIVE_ONLY`.
- 바꾸기: 헤더 [상태 변경] 팝업. 일시중지·폐쇄는 **사유 필수**, 폐쇄는 **운영 종료일 필수** + **재고가 남았거나 끝나지 않은 ASN이 있으면 거부**.
- 목록 일괄 처리는 운영중·일시중지만 (폐쇄는 한 건씩, 폐쇄된 센터는 건너뜀). 상태 변경·삭제는 운영사(전체 범위)만.

### 삭제

쓰인 적이 없는 센터만 지운다(논리 삭제, 대기 창고·로케이션도 함께 숨김). 보관 창고·재고 이력·ASN·배송권역·이용 화주사·소속 사용자 중 하나라도 있으면 거부하고 **폐쇄**를 안내한다.

## 상속 설정 (운영사 → 센터 → 화주사)

같은 설정을 여러 단계가 가질 때, **아래 단계가 정했으면 그 값, 비었으면(NULL) 위 단계 값**을 쓴다.

```
실제 값 = 화주사 값 ?? 센터 값 ?? 운영사 값
```

| 설정 | 운영사 | 센터 | 화주사 |
| --- | --- | --- | --- |
| 출고 마감 `ship_cutoff_time` | ○ | ○ (1차 화면) | — |
| 타임존 `timezone` | ○ (기본 Asia/Seoul) | ○ (2차) | — |
| 할당 규칙 `alloc_rule_cd` | ○ (기본 FIFO) | ○ (2차) | — |
| 로트·유통기한 관리 | ○ | ○ (2차) | ○ |
| 시리얼 관리 | ○ | ○ (2차) | — |

- 업무 코드는 칸을 직접 읽지 않고 `getEffectiveSetting(key, { centerId, shipperId? })`(`src/lib/settings/effective-setting.ts`)로 실제 값과 출처(`SHIPPER`·`CENTER`·`OPERATOR`)를 얻는다.
- 화면은 `InheritableField`로 그린다: "운영사 값 사용" 체크 = 저장 값 비움(NULL), 체크를 풀면 운영사 값으로 시작해 따로 입력 (docs/ui-guidelines.md "상속 칸").

## DB (마이그레이션 3개)

1. `20261116180000_center_spec` — `tb_center` 칸 추가·형식 변경, `tb_center_contact`·`tb_center_temp_zone` 생성, 검사 조건(코드 모양, 유형·상태 값, 일시중지·폐쇄 사유, 폐쇄일, 숫자 칸 ≥ 0, 사업자·종사업장·GLN 숫자, 보세 아니면 보세 칸 비움, 운영 요일 `[YN]{7}`, 할당 규칙), 상태 옮기기, 정렬순서 채우기, 공통코드 그룹 `CENTER_CONTACT_ROLE` 추가

전체 칸 정의: `docs/db-conventions.md` "tb_center".

## 남은 것

- 위도·경도: 카카오 우편번호는 좌표를 주지 않는다 → 칸만 두고 비움 (지도 API 연동 때 채움)
- 주소 필수는 화면·서버 입력 규칙에서만 (주소 없는 기존 센터가 있어 DB는 막지 않음). 기존 센터는 다음 저장 때 주소를 넣어야 한다
- 2차 칸 화면, 보세 세부 입력, 온도대별 면적·온도 범위(`tb_center_temp_zone`의 `area_m2`·`min_temp`·`max_temp`)
- 업무 코드에서 `getEffectiveSetting` 사용 (출고 마감·할당 규칙은 출고 기능 때)
