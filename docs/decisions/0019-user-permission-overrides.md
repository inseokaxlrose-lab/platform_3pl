# 0019. 사용자별 추가·제외 권한 화면

- 날짜: 2026-11-13
- 상태: 채택
- 관련: 0013 (권한 계산 공식), 0017 (권한그룹), 0018 (사용자 관리, 권한 상승 방지)
- 화면: `/admin/system/users/[id]`의 "개별 권한" 영역

## 결정

### 3단계 체크 표

- 칸 하나를 누를 때마다 **그룹대로 → ＋추가 → −제외 → 그룹대로** 순서로 바뀐다.
- "그룹대로"는 저장된 권한그룹에 있으면 회색 ✓, 없으면 빈칸으로 표시한다.
- 권한그룹과 **다르게 줄 권한만** 저장한다. 0013 공식은 "그룹 합 + 추가 − 제외"이고, 제외가 우선한다.
- 상태 계산은 화면·서버가 같이 쓰는 순수 함수로 한다 (`src/lib/permissions/override-state.ts`).

### 최종 권한 미리보기

- 서버와 **같은 계산 함수**(`computePermissions`)를 브라우저에서 바로 실행해 보여준다. 따라서 "조회가 없으면 버튼 권한도 무효" 같은 규칙이 미리보기에도 똑같이 적용된다.
- 계산 기준은 **저장된 권한그룹**이다. 위쪽 폼에서 그룹을 바꾸고 저장하지 않았다면 반영되지 않는다(화면에 안내).
- 기존 권한 체크 표(`PermissionMatrix`)를 읽기 전용으로 재사용한다. 운영사가 아닌 사용자는 시스템 메뉴 줄을 숨긴다(`includeOperatorOnly`).

### 저장 규칙 (`updateUserOverridesAction`, 권한 `system.users.update`)

| 규칙 | 이유 |
|---|---|
| 목록에 있는 코드, 사용자 유형의 영역 코드만 | 계산에서 무시될 값을 쌓지 않는다 |
| 운영사가 아닌 사용자에게 시스템 권한 추가·제외 불가 | 0018 권한 상승 방지와 같은 규칙 |
| 같은 코드를 추가와 제외에 동시에 넣을 수 없음 | 뜻이 모호하다 |
| 자기 자신의 개별 권한은 변경 불가 | 자기 권한을 올리거나, 실수로 시스템 권한을 빼서 잠기는 사고 방지 |
| 저장은 "전부 지우고 새로 넣기"를 한 트랜잭션으로 | 화면에 보이는 상태 = DB 상태 |

- 목록에서 사라진 옛 코드는 화면에 보이지 않고, 다음 저장 때 정리된다.
- 권한은 요청마다 다시 계산하므로 저장하면 상대방의 다음 화면 이동부터 적용된다.

## 확인

- 단위 테스트 4개, 컴포넌트 테스트 3개, DB 테스트 5개.
- 브라우저: 센터 직원("슈퍼 관리자" 그룹)의 품목 조회를 −제외하면 미리보기가 56 → 51개로 줄었다. 품목의 버튼 권한 5개가 함께 빠졌다. 저장 후 새로고침해도 유지됐다. 자기 자신의 화면에서는 모든 칸이 잠기고 안내 문구가 표시됐다.
