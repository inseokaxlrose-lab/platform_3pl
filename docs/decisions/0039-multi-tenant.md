# 0039. 멀티테넌트 — 여러 운영사가 한 시스템을 쓴다

- 날짜: 2026-11-15
- 상태: 채택 (3a·3b·3c 적용, 2026-11-15)
- 관련: 0016 (데이터 범위), 0024 (운영사 정보), 0038 (공통 칸), `docs/db-conventions.md` "운영사 칸"

## 배경

지금까지는 운영사가 1곳이라 고정 키 `1n`(`COMPANY_ID`)으로 한 줄만 두었다. 플랫폼으로 여러 3PL 운영사가 한 시스템을 쓰려면, 운영사마다 센터·화주사·공통코드·사용자를 따로 갖고 서로의 데이터를 볼 수 없어야 한다. 업무 화면(품목·재고)을 만들기 전에 바꿔야 고칠 곳이 적다.

## 결정 (사용자 결정: 추천안, 2026-11-15)

- 3단계로 나눠 적용: **3a 운영사 키·데이터 분리** → 3b 플랫폼 관리자·`/platform`·운영사 전환 → 3c 운영사 만들기(기본값 복사).
- 운영사 데이터가 들어가는 **11개 표에 `operator_id`를 직접** 붙인다: 사용자·권한그룹·센터·창고·로케이션·화주사·외부 코드·공통코드 그룹·공통코드·배송권역·단위.
  - 창고·로케이션처럼 센터를 거쳐 알 수 있는 표에도 직접 둔다 → 어느 표든 같은 방법(`operatorId`)으로 거른다.
  - 하위 표(담당자·이용 센터·소속·담당 지역 등)는 부모를 따른다. 운영사 담당자는 `operator_id`가 부모 키.
- 고유 규칙은 **같은 운영사 안에서만**: 센터·화주사·단위·공통코드 그룹 코드, 권한그룹 이름, 외부 코드. 로그인 아이디·이메일은 **전체에서 하나**.
- 거르기는 **두 겹**:
  1. 데이터 범위: `DataScope`가 항상 `operatorId`를 갖는다. `scopeFilter`가 운영사 조건을 자동으로 넣고, `isInScope`가 줄의 `operatorId`를 먼저 검사한다(운영사 칸을 읽지 않았으면 범위 밖 = 막는 쪽). 센터·화주사로 나누지 않는 데이터는 `operatorFilter(scope)`.
  2. Prisma 안전망: `createAction`이 로그인 사용자의 운영사로 "출입증"(`runInContext`, AsyncLocalStorage)을 만든다. 출입증 안에서는 11개 표의 읽기·수정·삭제에 지금 운영사 조건이 자동으로 붙고(다른 운영사를 적어도 덮어쓴다), 등록에 운영사가 자동으로 채워진다(다른 운영사를 적으면 개발 실수 오류).
- 출입증이 없는 곳(화면 조회 함수 `queries.ts`, 시드, 테스트 준비)은 자동 거르기가 없다 → 조회 함수는 반드시 범위(`scopeFilter`·`isInScope`·`operatorFilter`)를 쓴다. 새로 만드는 함수는 `requireOperatorId()`로 출입증을 요구한다.
- 전체에서 하나여야 하는 값(아이디·이메일) 중복 검사만 `acrossOperators()`로 운영사 거르기를 잠깐 끈다. 결과로 "있다/없다"만 쓴다.
- 코드 이름 `Company` → `Operator`(`src/lib/operator/`). 화면 주소·권한 코드(`master.company.*`)는 4단계 정의서 반영 때 바꾼다.

## 3a 결과 (2026-11-15)

- 마이그레이션 `_operator_tenant`: 칸 추가(빈 칸 허용) → 기존 줄을 가장 먼저 만든 운영사로 채움 → 빈 칸 금지. 운영사 정보를 등록하지 않은 채 데이터만 있는 DB는 기본 운영사("운영사")를 먼저 만든다. 담당자 표 `company_id`는 이름만 바꿔 데이터 보존.
- 운영사 정보 화면은 "내 운영사"를 고친다(처음 등록 개념 없음 — 운영사는 3c에서 플랫폼이 만든다).
- 공통코드 사용 수(`countCodeUsage`)는 운영사마다 센다. 화면 틀의 공통코드 목록도 내 운영사 것만.
- 외부 연동(I/F)용 `findByExternalCode`는 로그인 사용자가 없어 운영사 키를 직접 받는다.
- 시드: 예시 운영사를 먼저 만들고(가장 먼저 만든 운영사를 예시로 본다), 나머지는 그 운영사 출입증 안에서. 운영사별 함수는 `operatorId`를 받는다 → 3c에서 다시 쓴다.
- 검증: 빈 DB·개발 사본·"데이터만 있고 운영사 없는" DB 적용 후 스키마 차이 없음, 전체 테스트 497개 (두 운영사 격리 테스트 10개: 같은 코드 각자 사용·목록·수정/삭제 거부·수정 화면·아이디 전체 고유·안전망). 안전망·범위를 하나씩 일부러 꺼 보면 격리 테스트가 실패하는 것을 확인. 브라우저(목록·수정 화면, 임시 단위 등록 → `operator_id` 자동, 확인 후 삭제).

## 3b 결과 — 플랫폼 관리자·운영사 전환 (2026-11-15)

- 사용자 결정(추천안): 전환해 작업할 때는 **운영사 화면 전체 권한**, 플랫폼 메뉴 권한은 **`PLATFORM` 유형이면 전부**(권한그룹 없음 — 권한그룹은 운영사 데이터라서).
- 마이그레이션 `_platform_user`: 사용자 유형 `PLATFORM` + 검사 조건 "플랫폼 관리자 ⇔ 운영사 없음"(`tb_user_operator_matches_type`), 운영사 상태 `status_cd`(PENDING/ACTIVE/SUSPENDED/TERMINATED, 기존 ACTIVE) + 검사 조건.
- 영역 3개: `/admin`·`/portal`·`/platform`. 플랫폼 관리자는 로그인하면 `/platform`.
- 운영사가 ACTIVE가 아니면: 로그인 때 세션을 만들지 않고(`OPERATOR_DISABLED`), 이미 로그인한 사람도 `getCurrentUser`가 null → 다음 화면부터 막힌다.
- 운영사 전환: [이 운영사로 작업] → httpOnly·sameSite lax 세션 쿠키(`acting_operator`)에 운영사 키 → `/admin`. 쿠키는 매 요청 "플랫폼 관리자인지" 확인한 뒤에만 쓴다(운영사 사용자가 흉내 내도 무시). 전환 중: 범위 = 그 운영사 전체, 권한 = 운영사 화면 전체 + 플랫폼, 화면 맨 위 "○○ 운영사로 작업 중 [나가기]" 띠, 기록(등록·수정자)은 플랫폼 관리자 아이디. 대기·정지 운영사로도 전환할 수 있다(초기 설정·확인 대행).
- 플랫폼 화면: 홈, 운영사 목록(DataGrid — 운영사명·사업자번호·상태·사용자 수·등록일, 줄마다 [이 운영사로 작업]). 등록·상태 변경은 3c·4단계.
- 시드: 플랫폼 관리자(`SEED_PLATFORM_USERNAME`/`SEED_PLATFORM_PASSWORD`, 비어 있으면 건너뜀).
- 검증: 빈 DB·개발 사본 적용 후 스키마 차이 없음, 전체 테스트 515개 (권한·영역·범위, 운영사 상태별 로그인 막기, 세션 — 쿠키 흉내·전환 범위/권한·정지 후 기존 로그인 막기, 운영사 목록·전환·나가기, 전환 중 등록자 기록). 브라우저: 사용자 세션을 바꾸지 않으려고 플랫폼 관리자는 별도 세션(curl)으로 `/platform`·전환 전 `/admin` → `/platform`·전환 후 운영사 화면과 띠 확인 후 그 세션 삭제, 운영사 관리자 화면은 그대로(띠 없음, `/platform` → `/admin`).

## 3c 결과 — 운영사 만들기 (2026-11-15)

- 사용자 결정: 운영사를 등록하면 **관리자 계정을 자동으로** 만든다. 아이디는 `admin.○○`(뒷자리 입력, 예: `admin.nara`) — 로그인 아이디가 전체에서 하나라 모든 운영사를 `admin`으로 같게 할 수는 없어 같은 모양으로 맞췄다. **처음 비밀번호는 모든 운영사가 같은 값**(`.env`의 `SEED_ADMIN_PASSWORD`, 서버에서만 읽고 화면으로 보내지 않음).
- 기본값 정의를 `prisma/seed-*.ts` → `src/config/defaults/`(codes·units·roles)로 옮겼다(앱도 쓰므로). 견본 계정 정의만 `prisma/seed-samples.ts`.
- `provisionOperator(db, operatorId)`: 기본 공통코드·단위·권한그룹 4개를 "없으면 만들기"로 넣는다. 권한그룹 권한은 새로 만들 때만 채우고(운영사가 고친 권한을 지킨다), 개발 시드는 `syncGroupPermissions`로 정의와 똑같이 다시 맞춘다.
- `registerOperator`: 한 트랜잭션으로 운영사(운영) → 기본값 → 관리자(슈퍼 관리자 그룹). 작업 중인 운영사와 섞이지 않게 `acrossOperators` 안에서 새 운영사 키를 직접 넣는다. 계정 만들기(`createUserAccount`)는 바깥 트랜잭션을 받을 수 있게 했다.
- 플랫폼 [운영사 등록] 화면: 회사명·사업자등록번호(검증번호)·대표자·관리자 아이디 뒷자리. 운영사 코드 등 정의서의 나머지 칸은 4단계.
- 시드: 예시 운영사도 `provisionOperator`를 쓰고, 두 번째 견본 운영사 **나라물류(주)**(관리자 `admin.nara`, 센터 ICN — 예시 운영사와 같은 코드)를 운영 등록과 같은 함수로 만든다(운영 환경이면 건너뜀).
- 검증: 전체 테스트 523개 (기본값 넣기 — 여러 번·고친 값 유지·운영사별, 운영사 등록 — 한 번에 생성·새 관리자 로그인·작업 중 등록·아이디 겹침·입력 규칙·비밀번호 설정 없음·플랫폼만). 시드 두 번 실행 안전. 명령줄 확인: 플랫폼 등록 화면, `admin.nara`로 로그인하면 예시물류 센터 주소는 404·자기 센터는 열림·운영사 정보는 나라물류(주) (확인용 세션은 삭제).

## 남은 일

- 운영사 관리자의 처음 비밀번호가 모두 같다(사용자 결정, 개발 편의). 운영에 올리기 전에 운영사마다 다른 임시 비밀번호 + 처음 로그인 때 바꾸기 강제로 바꾼다.

## 하지 않은 것

- 창고의 운영사가 센터의 운영사와 같은지 DB 제약(복합 외래 키)으로 막지는 않았다. 등록 때 운영사가 출입증으로만 채워지고 센터 조회도 운영사로 걸러져 앱에서는 어긋날 수 없다. 필요해지면 `(center_id, operator_id)` 복합 외래 키로 강화한다.
- PostgreSQL 행 수준 보안(RLS)은 쓰지 않았다. 연결 하나를 여러 운영사가 나눠 쓰는 구조라 요청마다 세션 변수를 바꿔야 해서, 지금은 앱 두 겹으로 막는다.
