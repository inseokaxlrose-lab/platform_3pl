# 0067. 배포 방법

- 날짜: 2026-11-16
- 상태: **제안 — 사용자 결정 대기 (실제 배포는 하지 않음)**
- 관련: ROADMAP M7 "배포 방법 결정 및 첫 배포", 0001(기술 스택)

## 확인한 것 (배포 준비 상태)

- 운영 빌드(`next build`) 성공 — 모든 화면이 서버에서 그때그때 그리는 방식(ƒ)이라 서버가 필요하다.
- 환경 변수는 `.env.example`에 모두 있다: `DATABASE_URL`·`DIRECT_URL`, `BETTER_AUTH_SECRET`·`BETTER_AUTH_URL`, 첫 관리자·플랫폼 관리자 계정.
- 시드는 운영 환경(`NODE_ENV=production`)에서 **견본 계정·견본 센터/화주사를 건너뛴다** → 운영 DB에 시험 데이터가 들어가지 않는다.
- DB 구조 변경은 `prisma migrate deploy`로만 (마이그레이션 파일 그대로).

## 고를 것

| 안 | 내용 | 좋은 점 | 아쉬운 점 |
| --- | --- | --- | --- |
| **A. Vercel + 관리형 PostgreSQL (추천)** | 앱은 Vercel, DB는 Vercel Marketplace의 Postgres(예: Neon) 또는 다른 관리형 DB | git push만으로 배포, 미리보기 주소, 서버 관리 없음, Next.js 제작사라 궁합이 가장 좋음 | 사용량 따라 요금, 앱·DB 지역을 서울 가까이 맞춰야 빠름 |
| B. 클라우드 서버 1대 + Docker | 서버(예: AWS·NCP)에 앱 컨테이너 + DB | 비용 예측 쉬움, 국내 클라우드 선택 가능 | 서버 보안·백업·인증서·재시작을 직접 관리 |
| C. 사내 서버 | 고객사·자사 서버에 설치 | 데이터가 밖으로 안 나감 | 운영 부담 가장 큼, 지금 단계엔 과함 |

추천 이유: 지금은 MVP를 사람들에게 보여 주고 고치는 단계라 **서버 관리 없이 빨리 고쳐 올리는 것**이 가장 중요하다. 나중에 고객 요구(국내 데이터 보관 등)가 생기면 B로 옮길 수 있다 (Next.js + PostgreSQL 그대로).

## 첫 배포 순서 (A로 정하면)

1. 운영 DB 만들기 (서울 가까운 지역) → `DATABASE_URL`(연결 풀)·`DIRECT_URL`(직접 연결) 받기
2. Vercel 프로젝트 연결, 함수 지역을 DB와 같은 곳으로
3. 환경 변수 등록: `BETTER_AUTH_SECRET`은 새로 만든 긴 무작위 값, `BETTER_AUTH_URL`은 운영 주소, 첫 관리자 계정 값 — **견본 비밀번호는 넣지 않는다**
4. 운영 DB에 `prisma migrate deploy` → `prisma db seed`(기본 운영사·관리자만)
5. 배포 → 로그인·메뉴·입고 한 바퀴를 직접 확인 (브라우저 테스트 0065는 운영 DB에서 돌리지 않는다)

## 정해야 할 것 (사용자)

- A/B/C 중 어느 것, 운영 주소(도메인), DB 지역, 첫 관리자 아이디
- 계정 만들기·요금이 드는 일이라 **사용자가 직접 결정·가입한 뒤** 진행한다.
