## 결정

### 표 (`tb_shipper` 칸 추가)

| 묶음 | 칸 |
| --- | --- |
| 기본 정보 | 영문명·약칭, 화주 유형·업종(공통코드 `SHIPPER_TYPE`·`SHIPPER_INDUSTRY`), 사업자 구분·법인등록번호·종사업장번호·과세유형(운영사와 같은 상수), 정렬순서, 비고, 확장속성 |
| 연락처·주소 | 홈페이지, 국가(KR), 지번주소 (법정동코드는 운영사·센터처럼 두지 않음) |
| 계약·정산 | 계약시작일(필수, 기존은 등록일)·종료일(비면 기한 없음)·자동연장, 정산 주기(공통코드 `SETTLE_CYCLE`), 정산 마감일(비면 운영사 값), 결제 조건(일), 세금계산서 이메일 |
| 운영 설정 | 할당 규칙·로트·유통기한·시리얼·출고 마감(비면 위 단계), 입고·출고 최소 잔여일(비면 검사 안 함), 부분출고 허용, 재고 부족 시 처리 |
| 거래처·주문 정책 | 납품처 배송센터 미지정 처리, 납품처 자동 등록, 미등록 품목 허용, 주문번호 중복 기준 (포털·API 공통, 각 작업에서 사용) |
| 연동 | 연동 방식(PORTAL·API·FILE·EDI), API 사용 |
| 상태 | `PREPARING`·`ACTIVE`·`SUSPENDED`·`TERMINATED` + 상태 사유(일시정지·해지 필수) |

- **상수 (0030: 값에 따라 동작이 바뀜)**: 상태, 재고 부족 시 처리, 납품처 센터 정책, 주문번호 기준, 연동 방식. DB 검사 조건과 `shipper-codes.ts`의 값 목록이 같다.
- **공통코드 (분류·표시)**: 화주 유형, 업종, 정산 주기. `code-usage.ts`에 사용처를 등록하고, 새 운영사 기본값(`src/config/defaults/codes.ts`)과 기존 운영사(마이그레이션)에 넣었다.

### 이용 센터 (`tb_shipper_center` 칸 추가)

- 기본 센터(화주당 1개, 부분 고유), 이용 시작일·종료일, 상태(이용중/이용종료), 등록·수정자.
- 센터별 재정의(할당 규칙·로트·유통기한·시리얼·출고 마감) 칸은 DB만 만들었다. 화면은 2차다.
- 화면은 `EditableSubTable`이다. 하나뿐이면 저절로 기본이 된다.
- 빼거나 이용종료로 바꾸는 센터에 이 화주의 **재고·끝나지 않은 입고**가 있으면 막는다 (0035의 TODO 해결).
- 기존 화주: 센터 코드가 가장 앞인 이용 센터를 기본으로, 시작일은 화주 등록일로 채웠다.

### 담당자

- 공용 `contactSchema` + `isIfContact`로 만들었다.
- 화주사만 최대 10명이다. 연동 담당은 화주당 1명(부분 고유)이고 이메일이 필수다(DB 검사 조건).
- 정의서의 "IT 담당자는 이메일 필수"는 공통코드 값(IT)에 동작을 걸지 않으려고 **연동 담당자 이메일 필수**로 바꿨다.

### 상태별 동작

| 상태 | 데이터 범위·로그인 | 새 입고(ASN) | 품목·거래처 등록·포털 사용자 연결 |
| --- | --- | --- | --- |
| 준비중 | 됨 | 안 됨 | 됨 |
| 운영중 | 됨 | 됨 | 됨 |
| 일시정지 | 됨 (조회만 — 새 업무가 막혀 저절로) | 안 됨 | 안 됨 |
| 해지 | **로그인 막음** (`SHIPPER_DISABLED`), 범위에서 뺌 | 안 됨 | 안 됨 |

- 함수: `isShipperInScopeStatus`(해지만 뺌), `isShipperSetupStatus`·`SHIPPER_SETUP_ONLY`(준비중·운영중), 새 입고는 기존 `ACTIVE_ONLY`.
- 상태는 편집 화면 헤더의 [상태 변경] 팝업으로 바꾼다(센터와 같은 모양). 목록에서 여러 곳을 운영중·일시정지로 바꿀 수 있다(해지는 건너뜀).
- 해지는 재고·끝나지 않은 입고가 없을 때만 된다. 해지된 화주는 읽기 전용이다.
- PART 2에서 할 일: 해지하면 API 키를 모두 폐기한다 (`changeShipperStatus`의 TODO).

### 상속 (0073 확장) — 조사 의견

- `getEffectiveSetting`: **화주×센터 → 화주 → 센터 → 운영사** (구체적인 쪽이 이긴다). 출처 `SHIPPER_CENTER` 추가.
- 화주가 센터보다 앞서는 것이 맞다고 판단했다. 로트·할당 규칙·출고 마감은 **화주와의 계약 조건**이고, 센터 값은 그 센터의 기본 운영 방식이기 때문이다. 센터만의 사정이 화주와 다르면 화주×센터 칸으로 정한다.
- 타임존은 센터 → 운영사만 본다(화주 칸 없음).
- **품목 기본값**(로트·유통기한·라벨 단위)은 품목이 센터에 묶이지 않아 **품목 → 화주 → 운영사**로 본다. `shipperDefaultsSelect` + `shipperItemDefaults`로 모았고, 품목·ASN·검수·라벨·재고 변경이 모두 이 함수를 쓴다.

### 그 밖의 검사

- 화주 등록 때 운영사 `max_client_cnt` 한도를 본다 (해지 화주도 센다).
- 같은 운영사에 같은 사업자등록번호가 있으면 **막지 않고 알린다**(저장 후 notice, 사업부별 화주 가능).
- **전용 화주사**(창고·로케이션)는 그 센터를 이용 중(`ACTIVE`)인 화주만 지정할 수 있다 (`assertDedicatedShipper`). 로케이션은 바꿀 때만 검사한다.
- 센터 "이용 화주사 수"는 이미 `tb_shipper_center`를 세고 있었다.
