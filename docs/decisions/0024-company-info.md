# 0024. 운영사 정보 관리

- 날짜: 2026-11-13
- 상태: 채택
- 관련: PRD 4장 기준정보 1번, 0003 (위치 계층), 0015 (서버 액션), 0023 (도움말)
- 화면: `/admin/master/company`
- 코드: `src/lib/company/`, `src/app/admin/master/company/`, `src/components/common/address-fields.tsx`

## 결정

### 운영사는 1곳, 정보 화면 하나

- PRD상 MVP는 운영사 1곳 → 목록이 아니라 정보 화면 하나. DB는 고정 id(`default`) 한 줄(`Company`).
- 여러 운영사 SaaS로 바뀌면 이 표가 회사 단위의 기준이 된다.
- 수정 권한(`master.company.update`)이 없으면 읽기 전용(모든 칸 잠김, 저장·추가·주소 검색 버튼 없음).
- 운영사 정보는 모든 센터·화주사 데이터의 위에 있어 데이터 범위 제한이 없다 → 메뉴 권한으로만 막는다.
- 마지막으로 고친 사람·시각을 남기고 제목 아래에 보여준다.

### 관리 항목 (사용자 요청 반영)

| 묶음 | 항목 |
|---|---|
| 기본 정보 | 회사명*, 사업자등록번호*, 대표자, 업태, 종목 |
| 연락처 | 대표 전화, **팩스**, 대표 이메일 |
| 주소 | 우편번호, 주소, 상세주소 — **카카오 우편번호 서비스로 검색** |
| 담당자 | **최대 5명**: 담당 업무*, 담당자명*, 연락처, 이메일 (`CompanyContact`, 화면 순서대로 저장) |

- 로고 이미지는 파일 저장 장치가 필요해 이번에는 뺐다.

### 입력 규칙 (`company-schema.ts`, 화면·서버 공용)

- 사업자등록번호: 10자리 + **검증번호**(가중치 1,3,7,1,3,7,1,3,5 계산)까지 확인. 저장은 `000-00-00000` 모양.
- 전화·팩스: 숫자·하이픈, 숫자 8~12자리. 이메일 형식, 소문자로 저장. 우편번호 숫자 5자리.
- 빈 칸은 null로 저장.
- 화면에서 저장 전에 같은 규칙으로 먼저 검사해 **담당자 줄별 오류**까지 보여준다 (서버 응답의 칸별 오류는 담당자 몇 번째인지 알 수 없어서). 서버도 같은 규칙으로 다시 검사한다.
- 테스트용 사업자번호는 실제 회사 번호가 아닌, 검증번호 규칙으로 계산한 가상 번호를 쓴다.

### 공통 주소 입력 (`AddressFields`) — 센터·화주사·거래처에서도 재사용

- [주소 검색] → 팝업 안에 카카오 우편번호 화면을 넣는다(`embed`, 팝업 창 차단 걱정 없음). API 키 없음.
- 결과를 고르면 우편번호·주소를 채우고 **상세주소로 초점 이동**. 도로명 주소 + (법정동, 공동주택 건물명) — 카카오 안내 방식.
- 우편번호·주소는 검색으로만 채운다(읽기 전용). **검색 서비스를 불러오지 못하면**(사내망 차단 등) 안내 후 직접 입력으로 바뀐다.
- 외부 스크립트는 처음 [주소 검색]을 누를 때만 불러온다.

## 확인

- 테스트: 사업자번호 3개, 입력 규칙 4개, 서버 DB 4개, 폼 4개, 주소 입력 4개 (가짜 카카오로 선택·실패 흉내).
- 브라우저(admin):
  - 검증번호가 틀린 사업자번호는 칸 아래 오류와 함께 거부됐다.
  - 하이픈 없이 넣은 번호는 `220-81-12341`로 저장됐다.
  - **실제 카카오 검색**으로 "판교역로 166"을 골랐더니 `13529`와 주소가 채워졌고, 초점이 상세주소로 이동했다.
  - 담당자 2명이 순서대로 저장됐고, 이메일은 소문자로 저장됐다. "마지막 수정" 표시도 갱신됐다.
- `center.manager`(조회만): 읽기 전용(입력칸 19개 모두 잠김, 버튼 없음). `center.worker`(권한 없음): "접근 권한이 없습니다".
